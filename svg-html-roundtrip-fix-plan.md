# SVG/HTML Round-Trip, Blank-Line, and Alignment Fix Plan

## Objective

Make Markdown documents behave identically before and after:

- inserting an SVG or HTML block;
- adding a heading below that block;
- applying text alignment to the heading;
- saving and reopening the document;
- refreshing the page;
- editing the document after refresh.

The fix must preserve authored blank-line spacing, keep SVG/HTML blocks as single editor blocks, and ensure alignment always targets the intended Markdown block.

## Confirmed Problem Model

The current implementation has two different definitions of a “block”:

1. `serializeWithAlignment()` indexes every top-level ProseMirror child. This includes empty paragraphs generated by TipTap.
2. `extractAlignment()` indexes semantic Markdown blocks. Blank separators are not counted, while a fenced SVG/HTML block counts once.

When an SVG/HTML atom causes an empty paragraph to appear next to it, these indices diverge. For example:

```text
ProseMirror children:  svgBlock, empty paragraph, heading
Child indices:        0,        1,              2

Markdown blocks:      SVG fence, heading
Source indices:       0,          1
```

The persisted alignment marker can therefore refer to index `2`, while the loader expects source index `1`. The current loader-side filtering of empty paragraphs partially masks the issue but cannot correct markers created by the serializer.

The spacing problem comes from the same boundary. SVG and HTML are atom nodes rendered as fenced Markdown, while TipTap’s Markdown manager also adds block separators and reconstructs empty paragraphs from blank-line tokens. The application then translates between ordinary blank lines, `&nbsp;` paragraphs, and `markdown-spacer` divs. This creates multiple opportunities for an empty paragraph to be materialized or converted into an explicit spacer.

## Design Decisions

### 1. Define one canonical block-index model

Alignment indices must be based on semantic Markdown/editor blocks, not raw ProseMirror child positions.

Create one shared helper that walks the editor’s top-level document and returns entries such as:

```ts
type SourceBlock = {
  node: PMNode
  childIndex: number
  sourceIndex: number
}
```

The helper must:

- count SVG, HTML, Mermaid, code, table, paragraph, heading, list, and other real top-level nodes once;
- exclude parser-generated empty paragraphs used only as spacing artifacts;
- distinguish intentional empty paragraphs/spacers from accidental separator paragraphs;
- be used both when writing alignment directives and when applying them.

Do not maintain separate indexing logic in `serializeWithAlignment()`, `extractAlignment()`, and `applyAlignmentDirectives()`.

### 2. Make alignment metadata structural rather than position-fragile

The preferred short-term solution is to keep the trailing alignment marker but compute its indices from the shared semantic-block helper.

The marker should continue to look like:

```md
<!-- alignment: {"1":"center"} -->
```

The serializer must never use `editor.state.doc.forEach()` indices directly unless those indices have first been converted through the shared source-block mapping.

As a later improvement, consider block IDs or source anchors if positional alignment remains fragile when users insert/delete blocks before aligned content. That is outside the first fix and should not be mixed into the initial patch.

### 3. Separate structural separators from intentional spacing

The editor parser needs a representation for authored extra vertical gaps, but it must not treat every separator after an atom as an authored gap.

Use these rules:

- one normal Markdown separator between blocks remains structural;
- an intentional additional gap is represented explicitly by the existing spacer representation;
- parser-generated empty paragraphs caused only by a block separator are not persisted as spacers;
- `normalizeMarkdownForStorage()` must remain idempotent;
- `expandBlankRunsForParse()` must not add an empty paragraph merely because the preceding node is an SVG/HTML fence.

Before changing the implementation, document exact expected mappings for:

```text
paragraph\n\nheading
paragraph\n\n\nheading
svg fence\n\nheading
html fence\n\nheading
svg fence\n\n\nheading
html fence\n\n\nheading
```

### 4. Treat SVG and HTML atom serialization consistently

Review `SvgBlock.renderMarkdown()` and `HtmlBlock.renderMarkdown()` together. They should have the same block-boundary contract:

- the node body may contain internal newlines;
- the renderer should not add an ambiguous trailing blank line;
- the parent Markdown serializer should be responsible for inter-block separation;
- parsing and rendering the node should preserve its content exactly, apart from the documented fence newline requirement.

Add round-trip assertions for both nodes so a difference between SVG and HTML cannot reappear.

### 5. Keep preview rendering pure

The preview renderer should consume canonical Markdown only. It must not normalize persisted content or introduce transformations that later feed back into the editor.

The existing preview-only blank-gap rendering and alignment wrapping should be reviewed for two properties:

- it produces the intended visual spacing;
- it does not alter `markdown.value` or the saved source.

The preview path should be tested independently from the editor round-trip path.

## Implementation Sequence

### Phase 1: Add characterization tests before changing behavior

Build tests around the current helpers and, if practical, a TipTap editor instance using the production extensions.

Capture:

1. Markdown input.
2. Parsed top-level node names and attributes.
3. `editor.getMarkdown()` output.
4. `normalizeMarkdownForStorage()` output.
5. alignment marker output.
6. output after load → parse → apply alignment → edit → serialize.

The tests should explicitly record the current failures for:

- SVG followed by H2;
- HTML followed by H2;
- centered H2 after either block;
- multiple blank lines after either block;
- repeated save/reload cycles.

These are regression tests, not a request to preserve the broken output.

### Phase 2: Isolate and fix semantic block indexing

1. Add a shared semantic-block enumeration helper in `markdownAlignment.ts` or a small adjacent utility.
2. Update `serializeWithAlignment()` to use semantic source indices.
3. Update `applyAlignmentDirectives()` to use the same helper.
4. Remove duplicated assumptions about empty paragraphs.
5. Add diagnostics in tests that show the source index, ProseMirror child index, node type, and alignment target.

Important invariant:

```text
serialize → extract → parse → apply
```

must map every alignment directive back to the same semantic block.

### Phase 3: Stabilize SVG/HTML parse and serialization boundaries

1. Compare the exact Markdown produced by SVG and HTML nodes.
2. Verify how the installed `@tiptap/markdown` version tokenizes a fenced block followed by a heading.
3. Confirm whether the parser creates an empty paragraph for:

   - one separator newline;
   - one blank line;
   - multiple blank lines;
   - trailing EOF whitespace.

4. Adjust the custom node serializers or parse-input preparation so a structural separator after a fenced atom is not converted into an authored spacer.
5. Preserve intentional additional spacing through the explicit spacer representation.
6. Ensure the fix applies equally to `svgBlock` and `htmlBlock`.

Do not solve this by blindly stripping all blank lines around fenced blocks; that would destroy authored spacing.

### Phase 4: Simplify the persistence boundary

Review `normalizeMarkdownForStorage()` and `expandBlankRunsForParse()` against the test matrix.

Required properties:

- normalization is idempotent;
- parsing canonical content does not create new persisted spacers unintentionally;
- canonical content does not grow after repeated cycles;
- fenced SVG/HTML body content is not normalized as outer-document whitespace;
- legitimate blank lines inside code fences remain untouched;
- leading and trailing authored spacing follows a documented policy.

If the current `&nbsp;` conversion is retained for compatibility, isolate it as a legacy migration step. New ordinary blank-line cycles should not continually pass through `&nbsp;` and `markdown-spacer` conversions.

### Phase 5: Verify editor selection and alignment UX

After the structural fixes:

1. Place the cursor in the H2 immediately after an SVG block.
2. Click Center.
3. Confirm the H2 receives `textAlign: 'center'`.
4. Confirm the preceding empty paragraph, if any, remains unaligned or is not present.
5. Repeat after an HTML block.
6. Save, refresh, and confirm the H2 remains centered.
7. Insert a new block before the H2 and verify the marker remains correct according to the chosen positional model.

The toolbar’s `TextAlign` configuration should remain limited to paragraph-like nodes unless there is a separate product requirement to align atom nodes themselves.

### Phase 6: Verify preview, sharing, and PDF behavior

Confirm that the same canonical source produces matching results in:

- editor source state;
- local preview;
- public/shared preview;
- Markdown PDF export;
- downloaded Markdown.

Check that asynchronous preview rendering cannot reintroduce stale output after a rapid edit. The existing revision guard should remain intact.

## Required Test Matrix

### Plain Markdown

- paragraph → H2;
- paragraph → centered H2;
- multiple paragraphs with one blank line;
- multiple paragraphs with several blank lines;
- leading blank lines;
- trailing blank lines;
- H2 with no preceding block.

### SVG and HTML blocks

For each block type:

- block → H2;
- block → centered H2;
- block → right-aligned H2;
- block → one blank line → H2;
- block → multiple blank lines → H2;
- block → paragraph → H2;
- block at the beginning of the document;
- block at the end of the document;
- two adjacent blocks;
- block body containing internal blank lines;
- block body containing Markdown-looking text.

### Round-trip cycles

For every applicable case, repeat:

```text
source
→ parse into TipTap
→ apply alignment
→ serialize
→ normalize
→ save/reload
```

Run at least three cycles and assert that the canonical source, node sequence, spacer count, and alignment targets do not change.

### Interaction cases

- center the H2 before saving;
- center the H2 after refreshing;
- edit text inside the SVG block;
- edit text inside the HTML block;
- insert a paragraph below the atom;
- switch documents;
- switch public/authenticated mode if applicable;
- upload equivalent Markdown;
- rapidly edit while preview rendering is pending.

## Acceptance Criteria

The work is complete when:

- SVG and HTML blocks no longer create persistent unexpected blank lines around the following heading;
- ordinary one-blank-line separators remain stable after repeated refresh/save cycles;
- intentional additional spacing remains visible and stable;
- Center applies to the actual H2, not an adjacent empty paragraph;
- alignment survives save, reload, refresh, and the first edit after refresh;
- alignment markers are generated and consumed using the same semantic block index;
- SVG and HTML behave identically for equivalent structures;
- no changes occur to Typst source handling;
- preview, shared preview, downloaded Markdown, and PDF remain consistent;
- existing legacy alignment markers and legacy `&nbsp;` content remain readable or are migrated deterministically;
- tests prove idempotence over at least three round-trip cycles.

## Risks and Safeguards

### Risk: Removing a separator removes intended spacing

Safeguard: distinguish the single structural separator from additional authored spacing, and test one versus multiple blank lines separately.

### Risk: Existing documents use old alignment indices

Safeguard: retain backward-compatible reading for the current trailing marker format and add a migration/compatibility test before changing its interpretation.

### Risk: Empty paragraphs are legitimate authored content

Safeguard: only exclude empty paragraphs when they are demonstrably parser-generated separator artifacts. Preserve explicit spacer markers as semantic spacing nodes.

### Risk: SVG/HTML serializers diverge again

Safeguard: use parameterized tests with the same source structures for both node types.

### Risk: Preview appears fixed while saved source remains wrong

Safeguard: assert independently on editor JSON, canonical Markdown, preview HTML, and saved payloads.

## Suggested Implementation Handoff

The next coding pass should proceed in this order:

1. Add characterization and round-trip tests.
2. Implement the shared semantic block-index helper.
3. Correct alignment serialization and application.
4. Fix SVG/HTML fence boundary handling.
5. Rework or narrow blank-line conversion based on failing tests.
6. Run the complete round-trip and interaction matrix.
7. Inspect the final diff and confirm that only the intended files changed.

Do not begin with CSS changes. CSS can change visual margins, but it cannot correct the misplaced editor selection, incorrect alignment metadata, or persisted blank-line growth.
